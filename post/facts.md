## What it is
LazyLedger: drop receipt photos or a bank CSV into a web page; a local open-weight Gemma vision model extracts merchant/date/total/currency/category/line items as JSON into SQLite; plain pandas/statistics then flag recurring charges and likely zombie subscriptions, price hikes on the same merchant, outlier transactions (z-score + IQR), a monthly summary, and a next-month per-category forecast (linear + seasonal-naive). A button drafts a cancellation email with the same model. Stack: FastAPI, one static HTML page, pandas, Pillow, SQLite, httpx. Gemma backend is pluggable by env var (Ollama native, OpenAI-compatible, Google AI Studio style).

## Model setup actually used
Gemma 3 4B (gemma3:4b) through Ollama, running locally on a Windows laptop with 7.6 GB RAM and no GPU (CPU only). No data left the machine for the receipt tests.
I first tried free hosted Gemma 4 (google/gemma-4-31b-it:free and the 26B variant) via OpenRouter: every call returned 429, OpenRouter's message said the models were rate-limited upstream in a shared pool. I added backoff, still 429, so I switched to local. A Google AI Studio code path exists but was never run (no key).

## Sample-data demo (synthetic data, generated by a script, 99 rows over 7 months, Mar-Sep 2026)
Planted: a hidden zombie subscription (CloudVault Backup Pro, $12.99/mo), a price hike (StreamFlix HD $14.99 to $19.99, +33.4%), one outlier (MegaTech Electronics $1,249.00, z=9.7, 25.5x the Shopping median).
The app found all three. It also labelled StreamFlix a zombie (it is an active subscription with a price hike, so that label is debatable), reported 11 recurring charges including weekly groceries (noisy), 2 zombies with $395.76/yr "zombie drain" combined, and forecast $660.94 for next month in the screenshot run. The cancellation-email button was only tested with a canned mock model, never with real Gemma.

## Real receipts test (honest, small)
5 real receipts from the CORD v2 dataset test split (CC BY 4.0, https://github.com/clovaai/cord), Indonesian receipts with rupiah amounts like 60.000 and 174,600.
Run 1 (first working version): 3 of 5 totals correct. Failures: one receipt (truth total 28,000) came back as 100,000, the cash handed over rather than the total, with merchant returned as the string "null"; one Starbucks receipt (truth 174,600) came back as 194 and was marked OK (a silent error). Currency came back as USD for all five (they are rupiah). 4 of the 5 had no printed date. Each receipt took roughly 3 to 3.7 minutes on CPU (184-219 s).
A very first attempt discarded a whole receipt (merchant and total included) because the model returned the date as "Unknown", and parsed 60.000 as 60.
Fixes made: a missing date no longer discards the receipt (kept, flagged needs_review, today's date used); amounts like 60.000 / 28.000,50 are parsed as thousands separators; a check flags receipts whose total differs from the sum of line items by more than 25 percent; the string "null" no longer counts as a merchant.
After the fixes only 2 receipts were re-run (the machine ran out of memory before the rest): both totals correct (60,000 and 91,000), about 65 seconds each (not understood why faster). The other 3, including the two that had failed, were NOT re-run, so the safety check is covered by unit tests but not demonstrated on those receipts.
Unit tests: 18 passing, including the above.

## Why open weights mattered (only claims supported above)
Receipts and bank statements are personal: reading them with a local model meant nothing left the machine. No per-token bill, so an always-on folder watcher is affordable. When the hosted free tier of the same model family was rate limited, the open weights let me run it myself instead. Costs: slow (minutes per receipt on CPU), small model makes mistakes on messy receipts; hosted free tier was not dependable.
The sloth angle: the app is designed to be slow and unattended (drop files in an inbox folder and walk away).
